# Data model

Every table and collection, and why each one is shaped the way it is. The DDL itself lives in
the migration files, which are the authority; this explains the decisions behind it.

## The schemas

```
Postgres (one instance, three schemas - see 01 for why schema-per-service)
  auth.           users, refresh_tokens, outbox_events
  workspace.      workspaces, workspace_members, channels, channel_members,
                  dm_channel_keys, workspace_invitations, outbox_events,
                  processed_events, audit_log
  notification.   contacts, channels, workspaces, sent_notifications

MongoDB (slackclone_messages)
  messages, drafts, processed_events

Redis           presence, typing, the channel-access cache (no schema - all TTL keys)
OpenSearch      the `messages` index (a read model, rebuildable from Kafka)
```

---

## The rule that shapes all of it: no foreign keys across services

`workspace.channel_members.user_id` is a UUID with **no** foreign key to `auth.users`. Neither
does `messages.userId` in Mongo, or `notification.contacts.user_id`.

This is the single most consequential decision in the data model, so it is worth being precise
about what it costs and what it buys.

**What a cross-schema foreign key would give:** the database guarantees a membership row can
never reference a user who does not exist, and `ON DELETE CASCADE` cleans up automatically.
Genuinely valuable.

**What it would cost:** auth-service and workspace-service could never be deployed
independently, because a migration in one would lock tables in the other. They could never move
to separate database instances without a rewrite. And a slow query in one would hold locks the
other needs.

**What replaces it:** events. `user.deactivated` is the cascade — there is no `ON DELETE` to fall
back on, so the event *is* the mechanism. The residual risk is a window in which a channel
references a user who no longer exists, which the read path handles by rendering a placeholder.

That is not a theoretical trade. workspace-service had a `user.deactivated` handler and
auth-service published nothing, so the handler had never run once: a deleted account stayed in
every workspace and channel it had joined, kept appearing in member lists, and kept being
counted in channel fan-out. Both halves were individually correct. **With a foreign key that bug
is impossible; without one it is invisible.** See
[05 — Testing strategy](05-testing-strategy.md) for how it was eventually caught.

Inside a schema, foreign keys are used normally. `channels.workspace_id` references
`workspaces(id)` with `ON DELETE CASCADE`, because both belong to one service and are deployed
together.

## auth schema

### `users`

| Column | Notes |
|---|---|
| `id` | UUID, generated by the application rather than the database, so it is known before the insert and can go into an event payload in the same transaction |
| `email` | `CITEXT`, not `varchar`. Case-insensitive uniqueness has to be enforced by the *type*, not by lower-casing in Java — the day one code path forgets, two accounts exist for the same address and the login oracle is the least of the problems |
| `username` | `CITEXT`, unique, same reasoning |
| `password_hash` | BCrypt, nullable. Null means an SSO-only account. The nullability exists so the "this user has no local password" branch is a real state rather than a NullPointerException |
| `display_name`, `avatar_url` | Presentation only |
| `status_text`, `status_emoji` | The "In a meeting" line |
| `presence` | Last known value, as a fallback for a user with no live connection. The live answer is a Redis TTL key |
| `timezone` | IANA id. Validated on write, because `ZoneId.of` on a bad value throws at render time instead |
| `email_verified` | Gates sensitive actions, not login. Blocking login on verification is the fastest way to lose a signup |
| `is_active` | Soft delete. The row survives so references from other services resolve to something renderable |
| `version` | Optimistic locking. Two concurrent profile edits produce a 409 rather than one silently winning |

On the deactivation scrub: the email is **replaced** with `deleted+{id}@deleted.invalid`, not
nulled. The column is `NOT NULL` and unique, and overwriting it is what frees the original
address for re-registration — which is a real requirement, and the id suffix keeps the
replacement unique.

### `refresh_tokens`

| Column | Notes |
|---|---|
| `token_hash` | SHA-256 of the token, never the token. A database dump must not hand over live sessions |
| `family_id` | Groups a rotation chain, so reuse detection can revoke the whole chain in one statement |
| `used_at` | Non-null means redeemed. Presenting it again is the reuse signal |
| `revoked_at` | Distinguished from `used_at` on purpose: "used normally" and "revoked because of a suspected theft" are different facts and the second is worth auditing |
| `ip_address` | `inet`, with `@ColumnTransformer(write = "?::inet")` — see [02](02-low-level-design.md) |
| `user_agent` | So a "your sessions" screen can say *which* device |

Indexed on `(user_id, created_at DESC)` for the sessions list, and a partial index on active
tokens for the refresh path — the overwhelming majority of rows are spent and the hot query
never looks at them.

## workspace schema

### `workspaces` and `workspace_members`

The role lives on `workspace_members`, not on `users`. Someone can own their own workspace and be
a guest in a client's; a global role column makes that impossible to represent.

Roles are `OWNER > ADMIN > MEMBER > GUEST`, compared by rank rather than by equality so a check
reads "at least ADMIN".

`workspaces.slug` is `CITEXT` and immutable after creation, because it is part of a URL.

### `channels`

| Column | Notes |
|---|---|
| `name` | `CITEXT`, lowercase-only by check constraint. `#General` and `#general` would be two channels that look identical in the sidebar, which splits conversations in a way nobody can see |
| `type` | `PUBLIC`, `PRIVATE`, `DM`, `GROUP_DM`. One table rather than four, because the read path is identical for all of them and the alternative is a UNION in every sidebar query |
| `member_count` | Denormalised, with a `>= 0` check constraint. Counting on read is one query per channel per sidebar render |
| `last_message_at` | Denormalised for sidebar ordering. Updated by the `message.created` consumer, because message-service does not own this table |
| `is_archived` | Archive, not delete, so history survives. The internal access endpoint reports an archived channel as readable but not writable, which is the whole reason the distinction exists |

The uniqueness constraint is **partial**: unique on `(workspace_id, name)` only
`WHERE type IN ('PUBLIC','PRIVATE')`. DMs have no name, and without the partial clause every DM
would collide on null.

### `channel_members`

Carries the per-member read state, which is where several design decisions live:

| Column | Notes |
|---|---|
| `last_read_at` | A **watermark**, not a per-message read flag. One timestamp per member per channel instead of a row per message per member — the flag version is a table that grows with messages × members and is the single fastest way to make a chat app unscalable |
| `unread_count` | Maintained by the event consumer. The one non-idempotent write in the system, hence `processed_events` |
| `unread_mention_count` | Separate, because the UI treats them differently: an unread is bold text, a mention is a red badge. Collapsing them makes every channel look urgent |
| `notification_level`, `is_muted`, `is_starred` | Per-member preferences |
| `is_active` | Left-the-channel, kept so rejoining preserves the watermark |

The index that matters is `idx_channel_members_user_sidebar` on
`(user_id, workspace_id) INCLUDE (channel_id, unread_count, unread_mention_count, is_starred,
is_muted) WHERE is_active = true`. The `INCLUDE` makes it a covering index: the sidebar query —
the single most frequent query in the product — is answered from the index without touching the
table.

### `dm_channel_keys`

One row per distinct participant set: `participants_key` (SHA-256 of sorted ids, unique) →
`channel_id`. See [02](02-low-level-design.md) for why the hash is of a *sorted* list and why the
constraint rather than a lookup is what enforces it.

### `workspace_invitations`

`token_hash` is `CHAR(64)` — SHA-256 of the token in the emailed link, never the token. An
invitation token is a bearer credential: a database leak must not hand someone workspace access.
`expires_at` is not optional, because without it a forwarded invite email grants access forever.

The plaintext token exists in exactly two places: the email, and the event that triggers it.
Notably **not** in the API response — returning it would let any admin generate a link for an
address they do not control and use it themselves.

### `outbox_events`

The same shape in `auth` and `workspace`, from one mapped class in common-lib. See
[04 — Event catalogue](04-events.md).

The index is partial on `WHERE published_at IS NULL`. Published rows fall out of it
automatically, so it stays near-empty even once the table holds millions of historical events —
this is the textbook case for a partial index, and without it the poller gets slower every day
the service runs.

### `processed_events`

`(event_id, consumer)` as a composite primary key. Keyed on both because two different consumers
in one service may legitimately handle the same event, and keying on `event_id` alone would let
whichever ran first silently suppress the other — a bug that appears the day a second consumer is
added and looks like the new consumer simply not working.

Purged on a schedule down to a window that exceeds Kafka's retention, because a redelivery
cannot arrive for an event Kafka has already dropped.

### `audit_log`

Append-only, never updated or deleted by application code. `BIGSERIAL` rather than UUID: it is
never referenced by another table, so a monotonic integer gives better insert locality and a
smaller index.

## MongoDB

### `messages`

```json
{
  "_id": "uuid-string",
  "channelId": "...", "workspaceId": "...", "userId": "...",
  "type": "USER",
  "text": "ship it",
  "blocks": [],
  "threadRootId": null,
  "replyCount": 0,
  "mentions": ["..."],
  "mentionsEveryone": false,
  "reactions": [{ "emoji": "tada", "userIds": ["..."] }],
  "attachments": [],
  "isPinned": false,
  "clientMsgId": "...",
  "editCount": 0, "editedAt": null, "previousText": null,
  "isDeleted": false, "deletedAt": null, "deletedBy": null,
  "createdAt": "...", "updatedAt": "...",
  "pendingEvents": [ { "eventId": "...", "topic": "...", "payload": { } } ]
}
```

Why a document rather than rows:

- Reactions and attachments are **nested arrays**. Relationally that is three tables and three
  joins for every page of history.
- The whole document is written once and read many times, always by channel and time. There is
  no query that wants a message without its reactions.
- The shape evolves. Adding a field is a code change, not a migration over a billion rows.

`_id` is a string UUID, not an ObjectId. Generated by the application so it is known before the
insert, and consistent with every other id in the system — a message id that looks different
from a channel id is one more thing to remember.

Seven indexes, each for exactly one query, all created at startup by `MongoIndexInitializer`:

| Index | Serves |
|---|---|
| `(channelId, createdAt DESC)` | Channel scrollback — the most common query in the product. Compound in this order so an equality match on the prefix plus a sort on the next field is a straight index walk with no in-memory sort |
| `(threadRootId, createdAt)` partial | Thread view. Partial because the overwhelming majority of messages have no thread root, and indexing those nulls would double the index for nothing |
| `(mentions, createdAt DESC)` | "Mentions of me". Multikey — Mongo indexes each array element |
| `(channelId, clientMsgId)` **unique** partial | Idempotent send. The only index here that is about *correctness* rather than speed |
| `(channelId, isPinned, createdAt DESC)` partial | The pinned panel |
| `(workspaceId, userId, createdAt DESC)` | "My recent messages", export-my-data |
| `('pendingEvents.0', createdAt)` partial | The outbox poller's only query |

A `$jsonSchema` validator on the collection enforces required fields and types. Mongo being
schemaless is a property of the *engine*, not a licence for the data to be shapeless — the
validator catches a service writing a malformed document at the point of the mistake.

### `drafts`

Unsent text, so switching channels does not lose what you typed. Unique on `(userId,
channelId)`, with a **TTL index** expiring after 30 days — the one case where letting the
database delete data on a timer is exactly right.

### `processed_events`

The dedupe ledger for consumers that write to Mongo, with a TTL index. Same role as the Postgres
table of the same name.

## Redis

No schema. Four key shapes, all with expiry:

| Key | TTL | Why |
|---|---|---|
| `presence:{userId}` | 60s, refreshed by heartbeat | Expiry rather than a flag, because nothing runs when a laptop lid closes. A flag would read "online" for days |
| `presence:sessions:{userId}` | 60s | Counter, so closing one of two tabs does not mark you offline |
| `channel-access:{channelId}:{userId}` | 5s | The access-check cache. Short enough that removing someone takes effect almost immediately, long enough to absorb a burst of history requests |
| `rate:{userId}:{route}` | window | Gateway rate limiting |

## OpenSearch

The `messages` index is a **read model**: every document in it is derived from Kafka and can be
rebuilt by replaying the topic. Nothing in the product depends on it being authoritative, which
is what makes a reindex an operational task rather than a data-loss event.

One shard, zero replicas locally. A shard is both the unit of parallelism and a non-trivial
fixed cost — its own Lucene index, memory and file handles — and the common mistake is to
over-shard a small index "for growth", which makes every query slower because it has to fan out
and merge results from shards holding almost nothing.

`dynamic: strict`, so a document with an unmapped field is **rejected** rather than silently
adding one. A typo'd field name would otherwise create a field in the mapping forever, and
mappings cannot have fields removed.

See [02](02-low-level-design.md) for the analyser, and why there is no stemmer.

## notification schema

Two read models plus a ledger. Both read models exist so the service does not call auth-service
or workspace-service on the path of sending an email.

| Table | Notes |
|---|---|
| `contacts` | user id → email, display name, timezone. Built from `user.events`. `email` is nullable and every update uses `COALESCE`, because a `user.profile_updated` event carries no address — a blanket overwrite would null the stored one and silently destroy the ability to email that person, with no error anywhere |
| `channels` | channel id → name, workspace name. Built from `channel.events`, so an email can say `#deploys` rather than a UUID |
| `workspaces` | workspace id → name. Added after a bug: the name used to reach channels only via `workspace.created`, which applies it to the channels existing at that moment — none, since a workspace precedes its channels |
| `sent_notifications` | The dedupe ledger **and** the cooldown record. Two jobs in one table because both answer the same question — "have we already told this person about this?" — read by event id for dedupe and by `(recipient, channel, recency)` for the cooldown |

`sent_notifications.recipient_id` for an invitation is `uuid5` over the email address, because
the invitee may have no account. The ledger has to key on something, and deriving it
deterministically beats a nullable column with a second unique index for the one case that has no
user.

## Migrations

Flyway for the Java services, hand-written SQL, `ddl-auto: none` everywhere.

Hibernate's `update` will add a column and will never safely rename, drop or backfill one; it
cannot express a partial index or a check constraint; and it leaves the schema in whatever shape
the entity classes happened to have. The schema is reviewed like code.

Versioned (`V1__`, `V2__`) migrations for structure, repeatable (`R__`) for the dev seed. The
seeds also stage outbox events, so a fresh database produces the same downstream state a real
signup would — see [02](02-low-level-design.md).

notification-service applies its own schema at startup from `schema.sql`, with every statement
`IF NOT EXISTS`. A deliberate inconsistency: Flyway is a JVM tool, and wiring a JVM into a Python
image to run four `CREATE TABLE` statements is a worse trade. Alembic is the right answer the
moment that schema needs a backfill or a column rename.
